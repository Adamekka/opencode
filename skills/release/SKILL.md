# Release

Each new release request produces a new build. For a target explicitly not intended for production, keep the current marketing version and increment only the build. Otherwise, keep an existing unreleased marketing version unless a bug-fix release is being expanded into a feature release. Maintain one active cumulative Linear release issue for changes after the last build submitted to App Store Review, including earlier prepared builds in that range. Inspect and report the current state before making release changes.

## Inspect and report the current state

- Read the repository instructions and relevant project documentation. Inspect the worktree without editing. If pending app changes might belong in the release but their inclusion is unclear, ask one focused question and wait.
- Read the app's actual version, build, bundle identifier, and platform. For Xcode, identify the app target and its version settings across configurations; test-target versions are separate.
- Use the authenticated `asc` CLI as described in [App Store Connect queries](references/app-store-connect.md) to verify the publicly available version and its associated build. Also inspect newer uploads and their review, release, and TestFlight states. Verify the last build actually submitted to App Store Review separately from production.
- If App Store Connect access is unavailable, query Apple's live public App Store lookup by the app's bundle identifier and relevant storefront. Identify the platform and storefront checked. Report the public version and release date, and disclose that the lookup does not expose its build or private release states. Do not substitute Git markers or Linear statuses for evidence of public availability.
- Establish whether the app has ever been in production, including historical releases. A missing public lookup result or unavailable store access does not establish that it has never shipped. If it has never been in production, ask whether this target build is intended to go to production and wait, unless the user has already explicitly answered for this target. A yes keeps the legal-page workflow unchanged; a no uses build-only versioning and skips the entire legal-page section below. Apps with any prior production release always keep that section, even when the target build is unreleased. Preserve the answer when resuming the same target; ask again for a new target while the app has never shipped. Production intent does not authorize publishing.
- Enumerate release commits on the current branch's first-parent history whose entire subject matches `^[0-9]+\.[0-9]+\.[0-9]+ \([0-9]+\)$`. Match the production version/build to its release commit. When only the public version is available, use a Git build only if that version maps unambiguously to one release marker and no other evidence conflicts; state that Git supplied the build. If multiple builds share that version, require App Store Connect evidence or a user-confirmed build and commit. Never assume the newest same-version marker is production.
- Match the last submitted version/build to its first-parent release marker. Use this as the exclusive start of the Linear notes and tests. For a correction to a target already submitted, use the last qualifying submission before that target was first submitted. Ask if the submitted build or its Git marker cannot be resolved for the target.
- Resolve the app's Linear project and owning team. Reuse the active issue covering changes after the review baseline, even if the title names an earlier build or its notes still include older changes. Include every prepared release in the range, including locally prepared builds and builds with canceled issues. List the Git, store, and Linear states of known builds after production in the preflight report. Ask if the Linear destination is ambiguous.
- Complete the release prerequisites below before release changes.
- Before updating files, committing, or changing Linear, tell the user what is in production, all known versions/builds not in production and their states, the App Store Review baseline and the builds included in Linear, the current app configuration, changes after the latest release marker, the previous prepared release used as the testing baseline for existing checked features, CoreUtils freshness, localization results, CloudKit production schema deployment status, and any uncertainty or unavailable access. Include the sources checked, the proposed target when known, and whether legal-page work is required or explicitly skipped. If a required history boundary cannot be resolved, report what is known and ask one focused question before release changes.

## Determine the release

- For an app confirmed never to have been in production, report `Not yet in production`, keep the existing unreleased marketing version, and increment the build for a new request.
- If you confirm there is no qualifying prior App Store Review submission, use the initial history boundary from project documentation or ask the user to establish it. Record the boundary and its source in the release commit body or existing release documentation so it can be recovered on a resume. If there is no earlier included release marker, use the target as the first included release.
- Distinguish a new release from a request to resume the same unfinished release. For a resume, retain its target version/build instead of calculating another bump. Recheck production and the review baseline. Report any change in the version decision or Linear scope before making edits. If the release commit already exists, end the notes at that commit and skip the version update and commit steps. If the target is already in production, report that it has shipped; additional changes require a new version. If the unfinished target cannot be recovered from task context and Git, ask before proceeding.
- Before making a new marker, record the production version/build for version selection, the review baseline and earliest included version/build for Linear, and the latest local release marker for retesting.
- For a new release request, increment the current build number by one. If the user explicitly says the target is not intended for production, keep the current marketing version unchanged regardless of whether the changes are features or bug fixes, even when that version is already in production. Do not ask for a release kind solely to choose a version in this case. A resume still retains its existing version/build.
- When the current marketing version is already in production and the target is intended for production, use the release kind to choose the next marketing version: a feature release increments the minor version and resets the patch to zero, while a bug-fix release increments the patch. Keep the major version unchanged.
- For targets intended for production, if the current marketing version is still unreleased, keep it for the next build. For an app with a production release, upgrade an unreleased bug-fix version to the next minor version with patch zero only when the scope expands to a feature release. Determine that minor version from the verified production version. Do not increment the minor version again for another build of an already prepared feature release, and do not downgrade that feature version for subsequent bug fixes. For example, another feature build of unreleased `2.1.0 (30)` is `2.1.0 (31)`; expanding an unreleased `2.0.4` bug-fix release into a feature release can change it to `2.1.0`.
- A marketing version already published to production is immutable for subsequent production releases. For targets intended for production, never prepare additional changes under that version, even with a higher build number, and require the target marketing version to be numerically greater than production. For all targets, require the marketing version to be no lower than the previous prepared marketing version and a strictly greater build number for each new release request. An explicit version/build takes precedence only when these rules permit it. Resolve conflicting version information with the user rather than guessing.
- Determine whether the release kind changes the target marketing version before asking for it. Ask one focused question only when feature and bug-fix releases would produce different target marketing versions under these rules and the user has supplied neither the kind nor a valid full version/build. When both choices keep the same marketing version, increment the build without asking; this includes another build of an already prepared feature release, an app that has never shipped, and an explicitly non-production target. An unreleased bug-fix version can still require the question because expanding its scope to features changes the marketing version. Infer applicable Linear labels from the actual changes when no release kind is needed.

## Prepare the release notes

Read all commits after the review baseline through the target changes or the recorded target marker on a resume. Describe the combined behavior across the included builds, accounting for reversions and follow-up fixes. Inspect commit bodies, changed files, and relevant documentation when subjects alone do not explain the result.

Write the Linear issue title, description, and feature test list as described in [Linear release issue](references/release-issue.md).

## Commit and maintain the release issue

1. Update the app's version/build in its canonical configuration and all applicable app configurations. Preserve unrelated target settings and production data.
2. Load the `git-commit` skill and perform the configured checks relevant to the committed changes. Inspect the final diff and resolve failures within scope before committing. Honor the repository's review requirements.
3. Use the `review` skill for a review round before committing and updating Linear, for both production-intended and non-production builds. Review the exact target snapshot and cumulative changes, version/build settings, dependency, localization, and CloudKit production schema checks, release notes and test coverage, and legal-page work when required. Fix verified findings within the authorized scope and rerun affected checks; keep the preflight blockers and publishing permissions unchanged. Stop and report unresolved findings or required decisions instead of claiming the release is ready. For a resume with an existing release commit, review that recorded snapshot without silently changing it or skipping the review.
4. Commit only the release changes with the exact subject `version (build)`, for example `2.1.0 (30)`. This release marker intentionally overrides the usual Conventional Commit subject format so future releases can find the history boundary. Preserve the `git-commit` skill's verified model-author trailer requirement.
5. Maintain one active cumulative Linear release issue in the resolved app project and team. Search all release issues for an active issue covering changes after the review baseline. Update that original issue's target title, included releases, cumulative summary, and test list. Apply the [retesting rules](references/release-issue.md#preserve-verified-feature-tests) to its checked items; preserve assignment, status, priority, and unrelated labels. Merge overlapping feature tests instead of duplicating them. Create a new issue only when no active issue covers changes after the review baseline. The release request authorizes creating or updating this cumulative issue. Leave canceled and historical issues unchanged. When correcting an accidentally created duplicate, consolidate its unique content into the original issue and delete the obsolete duplicate when the user requests deletion. Apply these defaults to a newly created issue unless the user explicitly overrides them:
   - Status: resolve `Ready for Testing` in the app's team. If it is unavailable, ask instead of choosing another status.
   - Assignee: resolve and assign the authenticated user, `me`.
   - Priority: High, Linear priority `2`.
   - Labels: inspect the team's available active issue labels and infer applicable labels from the release kind and actual changes. Use existing labels and respect exclusive label groups. When correcting an existing release issue, preserve unrelated labels.
6. Read the issue back to verify its project, target and first included version/build in the title, verified review baseline in the description, included versions, complete cumulative description, build checkboxes, status, assignee, priority, and labels. Confirm the description contains only the four release-note sections and no operational details excluded by [Linear release issue](references/release-issue.md). Verify any requested obsolete-issue deletion separately. Report the production, review baseline, target and included versions/builds, commit hash, issue link, review and verification results, and legal-page completion or the explicit skip reason. In chat, report every checkbox state change by feature and build with its before/after state, every added checkbox with its state, and every removed checkbox with its previous state. Give the concrete retesting reason for each completed item reopened; group identical reasons when useful. Explicitly say when no checkboxes changed, were added, or were removed. Keep this operational report out of Linear.

If an operation fails or has an uncertain outcome, inspect the actual Git/Linear state before retrying. Resume the same release without incrementing again or duplicating a commit or issue. If the commit succeeded but Linear failed, preserve the commit and report the remaining issue-update blocker. A later independent release request creates a new build and follows the marketing-version rules above. Pushing, tagging, archiving, and publishing require their own request.
